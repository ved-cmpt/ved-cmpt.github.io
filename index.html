Problem

Governments, utilities, and other large organizations still run core systems such as billing and benefits on decades-old COBOL, whose business rules exist only in the code while its experts retire. AI can rewrite legacy code quickly, but a rewrite that silently changes a rounding or date rule can bill thousands of people incorrectly. Offshoot modernizes with AI while proving the new code behaves exactly like the old code, and keeps people in control of every approval.

Key features

  • Deterministic COBOL analysis: copybook expansion, call graph, data layouts, and dead-code detection, with no AI involved.
  • AI business-rule extraction where every rule must cite exact source lines. Hallucinated or unsupported rules are flagged and cannot be verified until a person fixes them.
  • AI migration of each COBOL module to C#, built and unit-tested in a network-less sandbox that blocks processes, networking, the file system, and reflection, with up to 3 repair attempts.
  • Golden-master equivalence: 500 seeded cases per module run through the real COBOL (GnuCOBOL) and the new C#, compared field by field, plus paragraph coverage and Stryker.NET mutation testing.
  • Five server-side gates and architect-only approval. The AI model can never approve anything.
  • Strangler-fig facade (YARP) that routes each module through legacy, shadow, and modern modes, plus an append-only audit log of every AI call and human decision.

Results

  • Rounding defect caught: the first C# rate calculator passed its own unit tests but matched only 484 of 500 cases. Each of the 16 mismatches was one cent, because C# rounded half a cent to the even cent (banker's rounding) where COBOL rounds half up. The module was blocked, and after one repair it matched 500 of 500.
  • All 4 migrated modules verified at 500 of 500 equivalent cases, with mutation scores of 78.75%–88.64% and paragraph coverage of 93.33%–100%.
  • Shadow mode compared 20 requests with 0 mismatches before promotion to the C# module.
  • Rule extraction in the mock pipeline: 95.65% precision and 88.00% recall, with both planted hallucinations caught.
  • Live Gemini, small samples: rule extraction on 2 programs reached 93.33% precision, 63.64% recall, and 100% valid source spans. A live migration of one module (RATECALC) compiled on the first try and matched 500 of 500 cases with a 93.94% mutation score, with no repair needed.
  • The prompt-injection comment was never obeyed, and the model made 0 approvals. Production smoke tests on the live site: 14 of 14 passed.

All results come from a synthetic COBOL billing system. Real-world users and cost savings were not measured.

Architecture flow

  1. A user works in the Angular UI.
  2. The FastAPI orchestrator runs each step as a job.
  3. Deterministic COBOL analysis builds the inventory, and the AI agent (Gemini or a mock) proposes rules, a plan, and C# code under strict contracts.
  4. Sandboxed runners build and run the code: GnuCOBOL for the legacy program, and a network-less .NET builder for the C#.
  5. The equivalence harness compares both on 500 seeded cases, and server-side gates decide what an architect can approve.
  6. PostgreSQL keeps every run and the append-only audit log, and the YARP strangler facade routes each module through legacy, shadow, and modern modes.

The model proposes, deterministic tooling verifies, and people approve.

Testing & quality

  • About 1,000 automated tests: 787 pytest, 163 Angular (Vitest), 26 .NET (xUnit), 18 Playwright and axe browser journeys in both themes, and a 14-test production smoke suite that also runs against the live site.
  • 136 characterization tests run the real COBOL against hand-computed expected values for each legacy quirk: half-up rounding, meter rollover, the two-digit-year window, truncation, and late-fee rules.
  • The same seed produces a byte-identical equivalence report, and a test checks it.
  • Sandbox attack tests: 9 of 9 hostile code samples fail the build, infinite loops hit the timeout, and a 4 GB allocation hits the memory limit.

  • GitHub Actions CI covers lint, strict types, dependency audits, a fresh-checkout Docker stack, a full-history secret scan, and a text-encoding check.

Real bugs found and fixed

  • A zombie-process leak in the .NET sandbox (454 processes against a limit of 512) that caused misleading build failures.
  • Login rate limits that silently never fired behind the hosting proxy.
  • A corrupted character in the live banner, traced to its root cause, with a new CI check to prevent it.
  • Gemini rejected the structured response schema, so 17 of 20 live calls failed. The schema moved into the prompt, with strict validation kept on the server.

Problem

Small organizations and campus IT help desks receive repetitive, free-text support requests, and staff spend time interpreting them, looking up documentation, and drafting answers. Generative AI could help, but uncontrolled AI can invent procedures, mishandle sensitive cases, or leak private data. IknowServiceAI uses AI to triage requests and draft answers from a trusted knowledge base, while code-enforced rules make sure a person reviews sensitive requests first.

Key features

  • AI triage of each request: category, priority, summary, and a suggested reply citing published knowledge-base articles, with every citation checked against what was actually retrieved.
  • A deterministic policy gate holds sensitive requests, such as account compromise or credential requests, for staff review. The AI cannot override it, and requesters see nothing until a person approves a reply.
  • Staff review workspace to approve, edit, or reject AI drafts, with an unsafe-reply check: a reply that asks for a password, for example, is refused.
  • Role-based access for requesters, support staff, and admins, plus an append-only audit trail of every decision.
  • Knowledge-base management with PostgreSQL full-text search, plus privacy redaction and prompt-injection defences.
  • Public demo mode with shared demo accounts, a daily data reset, and light and dark themes.

Results

  • Held all 22 sensitive cases for review and produced zero invented citations on a 43-case evaluation set; a live Gemini sample also held 3 of 3.
  • Mock mode on the same 43 cases: 81.4% exact category accuracy.
  • Live Gemini, small 10-case sample: zero invented citations, with a median latency of about 16 seconds.

The first evaluation run held only 86.4% of sensitive cases. The patterns were then fixed, and the 100% figure is on the same set used to tune them, so it says little about new text.

Screenshots

Architecture flow

  1. A user submits a request in the React UI.
  2. The FastAPI backend saves it, then redacts sensitive values such as emails, tokens, and keys.
  3. PostgreSQL full-text search retrieves published knowledge-base articles.
  4. The AI agent (Gemini or a built-in mock) proposes a category, priority, summary, and cited reply. Citations must match the retrieved, published articles.
  5. A deterministic policy gate holds any flagged request for staff, who approve, edit, or reject the draft.
  6. PostgreSQL (Neon) stores requests, replies, and the append-only audit trail.

The model only proposes text. It has no tools, and application code validates and writes everything.

Testing & quality

  • In CI: 876 backend and 242 frontend tests, plus end-to-end browser suites of 34 tests on the development stack and 46 on the production Docker image.
  • 172 axe accessibility checks with no findings, in light and dark themes, at desktop and 375 px mobile widths.
  • Security and adversarial tests: prompt injection, invented citation IDs, model attempts to skip review, cross-account access, duplicate or stale reviews, and rate limiting.
  • Mutation-style checks: safety controls were deliberately broken to confirm the tests catch it.
  • A 43-case evaluation set of ordinary, ambiguous, sensitive, and prompt-injection cases, plus a capped live Gemini sample.
  • Verified on the live deployment: security headers, secure cookies, session persistence after reload, rate limiting through the host's proxy (which found and fixed a real proxy-configuration bug), and data persistence after a redeploy.
  • Every user journey also tested by hand in the browser, locally and on the live site.

Problem

Home-contents insurance claims for damaged or lost belongings need a clear path from submission to decision. Policyholders need to see where their claim stands, and adjusters need consistent, explainable checks with a full record of who did what. ClaimWillow models this workflow for a fictional insurer, using synthetic data, as a demonstration of enterprise workflow design and layered test automation.

Key features

  • Policyholder claim intake: save drafts, submit against an active policy, and keep a snapshot of the policy's coverage limit, deductible, and period taken at submission.
  • Six deterministic validation rules (R1–R6): required inputs, policy active on the incident date, estimate against the coverage limit, deductible, potential duplicates, and completeness. Each finding is stored and explained in plain language.
  • Adjuster queue and review lifecycle: assign, start review, request more information, policyholder response, approve or reject, and close. Illegal transitions are rejected.
  • Safe concurrent editing: optimistic locking returns HTTP 409 on conflicting updates.
  • An append-only audit timeline for every important action, plus private evidence uploads (PDF, PNG, or JPEG, with type and size checks and role-checked downloads).
  • Staff reporting with CSV export, and admin user management to enable or disable accounts.

Results

  • All 10 browser acceptance scenarios from the specification pass (96 steps), and CI is green on main.
  • Latest CI on main: 75 backend unit, 60 backend integration, and 30 frontend tests, all passing.
  • A concurrency test confirms that only 1 of 6 simultaneous assignments succeeds; the others get a clear conflict response.
  • Deployed and working at $0 hosting cost on Render and Neon.

Screenshots

Architecture flow

  1. A policyholder, adjuster, or admin uses the React and TypeScript UI.
  2. The Spring Boot REST API authenticates with a server-side session and checks a CSRF token on every change.
  3. Claim services run the review state machine and rules R1–R6, and record audit events in the same transaction.
  4. JPA and Flyway map and migrate the data in PostgreSQL (Neon in production).

One Docker container on Render serves both the UI and the API.

Testing & quality

  • Backend unit tests (JUnit 5 and Mockito) for the rules, money calculations with BigDecimal, and state transitions.
  • Integration tests against a real PostgreSQL in Docker (Testcontainers): migrations, the claim lifecycle, 401/403/404 access boundaries, CSRF enforcement, a concurrent-assignment race, transaction rollback on a database failure, attachment authorization, and CSV export.
  • Frontend tests (Vitest and React Testing Library) for forms, validation messages, and role-specific actions.
  • 10 browser acceptance scenarios (Cucumber and Selenium in headless Chrome), with screenshots captured on failure.
  • GitHub Actions CI on every pull request, with a protected main branch that requires CI to pass. The production Docker image was smoke-tested under a 512 MB memory limit.
  • Checked by hand locally and on the live site: logins for each role, policies, claims, and a submitted claim showing its rule findings and history.

Team

Problem

Deferred exams relied on manual scheduling and scattered information, which led to booking conflicts, limited room capacity, communication delays, and repetitive administrative work. The goal was one system for students, faculty, administrators, and proctoring.

System features, built by the team

  • Role-based dashboards with their own navigation, data, quick actions, and permissions.
  • Exam booking by date, room, and time slot, with seat tracking, conflict checks, and transactional seat updates.
  • Exam lifecycle: Booked, Fee Paid, Checked In, Exam Finished, Dropped Off, Faculty Received.

Architecture flow

MVVM data flow: Compose UI, ViewModel, Repository or Firebase services, Firestore or Cloud Functions, real-time state, updated UI.

DuckBot action pipeline:

  1. A user types a request in the chat.
  2. The ViewModel adds role and policy context.
  3. The request goes to the Gemini API.
  4. Structured action markers are parsed from the response.
  5. The action registry checks what the role supports.
  6. A wizard collects any missing inputs.
  7. The secure action service calls Cloud Functions with authentication.
  8. Server-side code validates permissions and performs the operation.
  9. The result returns to the conversation.

An AI-generated request is not treated as authorization: sensitive operations go through protected backend endpoints.

Testing

JUnit, AndroidX Test with Espresso, Compose UI Test, and ArchUnit. The team tracked and fixed defects iteratively across notification navigation, booking forms, account management, and availability.

My contributions
